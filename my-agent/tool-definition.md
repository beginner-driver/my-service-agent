# 도구 정의서 — 제출서류 검증 챗봇

각 도구는 이미 인덱싱된 `documents/{기관}_{공고}/` 데이터를 조회만 한다. 인덱싱 자체는 도구가 아니라 별도 유틸리티의 역할이다 ([`README.md`](../README.md) "실행하지 않은 것과 이유" 참조).

---

## `get_rfp_requirements`

**이름 / 한 문장.** 지정된 기관·공고의 제출서류 요건 목록을 조회한다.

**쓰는 때 / 안 쓰는 때.**
- 쓰는 때: 검증 대화를 시작할 때, 대상 event(기관·공고)가 확정된 직후 항상 최초 1회 호출한다.
- 안 쓰는 때: event가 여러 후보로 모호할 때는 호출하지 않고 먼저 사용자에게 되물어 확정한다. 같은 대화에서 이미 조회한 event를 재조회하지 않는다.

**인자 스키마.**
| 인자 | 필수 | 타입 | 허용값 / 처리 |
|---|---|---|---|
| `event_id` | 필수 | string | `documents/{기관}_{공고}/` 폴더명과 1:1 대응, 사전 인덱싱된 값만 허용. 누락 시 도구를 호출하지 않고 후보 목록을 제시해 사용자가 고르게 한다. |

**반환 형식.**
- `requirements[]`: `{서류명, 필수여부, 형식조건, 근거조항(조번호/페이지)}`
- 오류코드: `NOTICE_NOT_FOUND` (해당 event_id 인덱스 없음)

**실패 뒤 행동.** `NOTICE_NOT_FOUND` 1회 발생 시 event_id 철자를 재확인 요청한다. 2회 연속 실패하면 "인덱싱이 안 된 건일 수 있다"고 안내하고 보류한다.

## `check_document_checklist`

**이름 / 한 문장.** 보유 서류 목록을 요건과 대조해 항목별 충족·누락 상태를 표시한다.

**쓰는 때 / 안 쓰는 때.**
- 쓰는 때: `get_rfp_requirements`로 요건을 이미 확보한 뒤, 사용자가 자신이 준비한 서류 목록을 제시했을 때.
- 안 쓰는 때: 요건 조회가 선행되지 않았을 때는 호출하지 않는다(순서 강제). 서류 목록 없이 "검증해줘"라고만 했을 때는 먼저 목록을 요청한다.

**인자 스키마.**
| 인자 | 필수 | 타입 | 허용값 / 처리 |
|---|---|---|---|
| `event_id` | 필수 | string | 위와 동일 |
| `submitted_documents` | 필수 | array of `{서류명: string, 비고?: string}` | 빈 배열 불허. 빈 배열이면 도구를 호출하지 않고 목록을 재요청한다. |

**반환 형식.**
- `checklist[]`: `{서류명, 상태(충족/누락/확인필요), 근거조항}`
- `missing_count`
- 오류코드: `EMPTY_CHECKLIST`

**실패 뒤 행동.** 목록이 비어있으면 1회 재요청한다. 형식이 애매하면(서류명만 나열되고 구분이 안 되면) 입력 예시를 보여주고 재입력을 요청한다. 2회 연속 실패하면 보류한다.

## `validate_document_detail`

**이름 / 한 문장.** 개별 서류의 발급일·유효기간·날인 등 세부조건 충족 여부를 확인한다.

**쓰는 때 / 안 쓰는 때.**
- 쓰는 때: 체크리스트상의 특정 서류에 대해 사용자가 세부조건(유효기간, 발급일자, 날인 여부 등)을 구체적으로 물을 때.
- 안 쓰는 때: 서류 존재 여부만 궁금한 경우는 `check_document_checklist`로 충분하므로 호출하지 않는다. 근거조항에 세부조건이 아예 명시되지 않은 항목은 추측하지 않고 `FIELD_NOT_SPECIFIED_IN_NOTICE`를 반환한다.

**인자 스키마.**
| 인자 | 필수 | 타입 | 허용값 / 처리 |
|---|---|---|---|
| `event_id` | 필수 | string | 위와 동일 |
| `document_name` | 필수 | string | 체크리스트에 존재하는 서류명과 일치해야 함 |
| `detail_fields` | 필수 | array of string | 최소 1개 (예: `발급일자`, `유효기간`, `날인여부`) |

**반환 형식.**
- `result[]`: `{field, 충족여부(충족/미충족/확인필요), 근거조항}`
- 오류코드: `FIELD_NOT_SPECIFIED_IN_NOTICE` (공고에 해당 조건 명시 없음)

**실패 뒤 행동.** `FIELD_NOT_SPECIFIED_IN_NOTICE` 발생 시 추측하지 않고 즉시 확인필요로 반환한다. 같은 질문이 반복돼도 재시도하지 않는다 — 원문에 없는 정보는 재조회해도 나오지 않기 때문이다.

## `escalate_to_reviewer` (쓰기)

**이름 / 한 문장.** 판정이 불명확하거나 사용자가 결과에 이의를 제기할 때 담당자 검토를 요청한다.

**쓰는 때 / 안 쓰는 때.**
- 쓰는 때: `AMBIGUOUS_REQUIREMENT` 또는 `FIELD_NOT_SPECIFIED_IN_NOTICE`가 반복될 때, 사용자가 자동판정 결과에 명시적으로 이의를 제기할 때, 요건 범위를 벗어난 법률자문성 질문을 받았을 때.
- 안 쓰는 때: 조회·대조만으로 해결되는 경우, 명백한 누락(재확인이 필요 없는 경우)은 티켓 없이 바로 지적한다.

**인자 스키마.**
| 인자 | 필수 | 타입 | 허용값 / 처리 |
|---|---|---|---|
| `event_id` | 필수 | string | 위와 동일 |
| `issue_summary` | 필수 | string | 이관 사유 요약 |
| `user_confirmed` | 필수 | boolean | 사용자가 "보내줘"라고 명시적으로 확인했는지. `false`면 도구를 호출하지 않고 먼저 확인 질문을 한다. |

**반환 형식.**
- `ticket_id`, 처리 예상 안내
- 오류코드: `TICKET_CREATE_FAILED`

**실패 뒤 행동.** 생성 실패 시 1회 재시도한다. 재실패하면 자동 이관을 포기하고 사용자에게 담당자 직접 연락처를 안내한다.
