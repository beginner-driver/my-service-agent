# 제출서류 검증 챗봇 — my-service-agent

## 서비스 소개

특정 기관이 공지한 제안요청서(RFP)의 제출서류 기준에 맞춰, 사용자가 준비한 서류가 요건을 충족하는지 검증하고 부족한 부분을 지적하는 챗봇이다. 대상 사용자는 입찰·제안에 참여하는 기업의 서류 준비 담당자다.

기관·공고 원문 문서는 `documents/{기관명}_{공고명}/` 폴더에 보관하고, 사용자가 별도 유틸리티로 이 폴더를 읽어들여 검색 가능한 형태(RAG 인덱스)로 만든다. 챗봇은 대화 중 이 인덱스를 도구로 조회해서만 답하며, 도구 조회 없이는 어떤 항목도 "충족"으로 확정하지 않는다. 여러 기관·공고 건을 오래 걸쳐 재사용하는 것을 전제로 설계했다 — 한 건이 끝나도 인덱스를 지우지 않고, 새 건이 생기면 새 폴더·새 인덱스만 추가한다.

## 도구별 역할과 분리 이유

검증은 "요건 확인 → 전체 대조 → 세부 확인"의 세 단계로 점점 좁혀 들어가고, 여기에 필요할 때만 담당자를 부르는 이관 도구가 더해진다. 전체 정의는 [`my-agent/tool-definition.md`](my-agent/tool-definition.md)에 있고, 여기서는 왜 이렇게 나눴는지를 설명한다.

**`get_rfp_requirements` — 이 공고에서 뭘 내야 하는지 목록부터 가져온다.** 공고 원문을 검색해 제출서류 목록·필수 여부·형식조건을 조항 번호와 함께 가져온다. 대화가 시작되면 항상 가장 먼저 호출된다 — 이 목록이 없으면 뒤의 두 도구가 뭘 대조해야 할지 알 수 없기 때문이다.

**`check_document_checklist` — 보유 서류를 요건 목록과 전체 대조한다.** 사용자가 준비했다고 말한 서류 목록을 앞서 가져온 요건과 맞대어, 항목별로 충족·누락·확인필요를 표시한다. 여기까지는 "뭐가 빠졌는지"는 알 수 있지만, "빠지진 않은 서류가 조건에 정확히 맞는지"는 아직 확인하지 않는다.

**`validate_document_detail` — 서류 하나의 세부조건을 더 깊게 확인한다.** 유효기간, 발급일, 날인 여부처럼 존재 여부만으로는 판단할 수 없는 조건을 확인한다. 체크리스트에서 "있음"으로 표시된 서류도 세부조건은 별도로 이 도구가 확인해야 알 수 있다.

**세 단계로 나눈 이유.** 이 셋을 한 도구로 합치면 서류 이름만 물어봐도 매번 세부조건까지 통째로 검색하게 되어 느려지고 답변도 필요 이상으로 길어진다. 대신 사용자가 궁금해하는 깊이만큼만 도구가 호출되도록 나눴다 — "제출서류 뭐야?"엔 1번만, "이거면 충분해?"엔 1→2번까지, "이 서류 유효기간 괜찮아?"처럼 콕 집어 물으면 2→3번까지만 호출된다.

## 설계 결정 요약

**도구를 4개로 한정한 이유.** 검증 흐름을 "요건 조회 → 보유 서류 대조 → 세부조건 확인 → 필요시 담당자 이관"의 네 단계로 나눴을 때 각 단계가 서로 겹치지 않게 딱 떨어졌다. 다섯 번째 도구를 추가하면 기존 네 도구 중 하나와 책임이 겹치게 되어, 대신 필요하면 기존 도구의 반환 필드를 늘리는 쪽을 택했다.

**권한을 읽기 3개·쓰기 1개로 나눈 기준.** 조회·대조·세부조건 확인은 사용자·기관에 어떤 영향도 남기지 않는 조회 동작이라 자유 호출로 뒀다. 담당자 이관(`escalate_to_reviewer`)만 실제 사람의 시간을 소모시키는 되돌리기 어려운 동작이라, 실행 전 사용자의 명시적 확인을 요구하도록 승인을 걸었다.

**실패 뒤 행동을 "추측 대신 확인필요"로 정한 기준.** 이 챗봇의 실패 비용은 "틀린 답으로 서류를 잘못 준비해 입찰 자격을 잃는 것"이라 침묵이나 추측보다 훨씬 크다. 그래서 근거조항이 불명확한 모든 경우에 재시도나 짐작 대신 "확인필요"로 멈추고 원문을 인용하도록 통일했다.

## 실행하지 않은 것과 이유

**인덱싱은 챗봇 도구로 노출하지 않았다.** 문서 재구축(임베딩 계산)은 시간이 걸리는 파이프라인 작업이라 대화형 조회와 성격이 달라, 사용자가 별도 GUI 유틸리티로 직접 실행하도록 분리했다. 챗봇이 스스로 판단해 재인덱싱을 트리거하게 두면 대화 중 응답이 예측 없이 몇 분씩 멎을 위험이 있었다.

**Claude API 직접 연동은 구현하지 않았다.** 이 저장소가 만드는 것은 도구(MCP 서버)뿐이고, 실제 질문 이해와 답변 생성은 MCP 클라이언트(Claude Desktop 등)가 맡도록 역할을 나눴다. 클라이언트가 이미 대화·판단 역할을 하고 있어 별도로 API를 호출하는 코드를 둘 이유가 없었다.

**벡터 인덱스를 기관·공고별로 통합하지 않고 각각 영구 분리 보관하기로 했다.** 여러 건을 넘나들며 재사용하는 시스템이라, 인덱스를 합치면 이전 기관 자료 재조회가 어려워지고 검색 결과에 서로 다른 기관의 조항이 섞일 위험이 있었다.

**실제 MCP 서버 코드·GUI 인덱싱 유틸리티·벡터DB는 구현하지 않았다.** 이번 과제 범위는 경계와 판단 기준을 문서로 정리하는 것이라, `design-packet.md`와 `my-agent/tool-definition.md`에 계약을 명세하는 데까지만 진행했다.

## 다음에 측정할 지점

- `AMBIGUOUS_REQUIREMENT`·`FIELD_NOT_SPECIFIED_IN_NOTICE` 오류가 실제로 얼마나 자주 발생하는지 — 너무 잦으면 원문 파싱 방식(청크 분할 기준)을 재검토
- `escalate_to_reviewer` 호출 대비 실제 담당자 개입이 필요했던 비율 — 낮으면 이관 조건을 더 좁혀도 됨
- 사용자가 같은 event 안에서 몇 번이나 도구를 재호출하는지 — 대화 시작 시 event 확정 절차가 충분히 매끄러운지의 지표
